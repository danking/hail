* Hail 2022 Vision
** Query on Batch (QOB)
Our absolute number one priority is a fully functional Hail Batch Backend for Hail Query.

This has a number of important benefits:
1. Reunify the goals and priorities of the two teams.
2. Enable Hail team (not Dataproc) to profit from *our work* buiding Hail.
3. Improve operational experience for gnomAD, improve support experience for Hail team.
4. Enable Hail to scale to 100,000+ cores.
5. Break free of Spark scatter-gather, enabling the DAGs necessary for Big Linear Algebra.
6. Enable caching of blob storage via a scalable preemptible-tolerant cache service.
7. Align incentives towards native code: containerized binaries >>> JVM bytecode.
8. Provide a zero-operational-burden data store for portals.

The path there:
1. [INPROGRESS] Preemptible-safe shuffle.
2. [INPROGRESS] Sufficiently fast scheduling to run all the tests.
3. [INPROGRESS] Lower all remaining operations.
4. Quality of life improvements (e.g. automatic upload of referenced local files).
5. Reduce JVMJob no-op job round trip time by an order of magnitude.
6. Implement driver-side code as a resumable, persistent state machine.
7. Develop the cache service as necessary to serve the needs of Hail Query
8. Develop a solution that does not require an always-on k8s cluster.

The Intermediate Goal:
1. 2022Q1: Query on Batch for large, non-interactive batches (e.g. gnomAD v4).

Soft announcement target: 2022-04-04 Hail Team ATGU Lab Meeting.

** Tight integration of QoB and Batch
Once we have QoB, we can push hard on deep integration between Batch and Query. This is a powerful
and completely novel system. None of our competitors can schedule both arbitrary binaries with
dataframe jobs.

Benefits:
1. SAIGE-all-the-intervals and REGENIE can be implemented as pip-installable Hail scripts.
2. Enable fully-automated, continuous analysis: go from gVCF to p-values in one failure-resilient,
   resumable Hail Batch.

The path there:
1. Support dynamically elaborated DAGs (e.g. Hail Query) in one Batch (i.e. open batches).
2. Batch library support for common patterns of communication between Query and binaries.

** Query User Experience
All of the above is naught if we don't provide the users what they need. Improving the user
experience is an iterative process that should involve conversations with users and not-yet-users. A
few areas, some of which we're working on, that need improvement:
- plotting
- friendly, efficient interface for dictionaries with finite key-sets
- general (sliding) windowed aggregations
- new methods (e.g. REGENIE, LMMs, etc.)

** Datasets API / Annotation DB Excellence

Get gnomAD and SEQR using the annotation DB. If we build something they like to use, then we've
built something everyone will like.

** Batch Operational Excellence

1. Squash the filesystem corruption / not executable / not existent issue.
2. Completely eliminate Docker.
3. Billing granularity must be shorter than 24 hours.

**** High level framing of system
#+begin_quote
Building Chubby was an engineering effort requried to fill the needs mentioned above; it was not

**** Motivations
Googlers applied ad-hoc approaches to leader election which lead, in some systems, to unnecessary
(but harmless) duplicated work and, in other systems, operator intervention (and thus loss of
availability).
**** Do they talk about users or not?
Yes, quite a bit. The paper is very focused on how to build a system to serve the daily, practical
needs of software engineers at Google.
e.g.:
- SWEs do not design for availability
- SWEs do not want to choose a cache time out
- SWEs are comforatble with locks but less comfortable with consensus
- SWEs find inconsistent caching confusing
- SWEs, in practice, will poll files
**** What do they care about? What do they want readers to get out of the paper?
They have an explicit Lessons learned section. I think this might reference to the "Center for Army
Lessons Learned". It seems like they highlight a number of specific practical lessons in engineering
distributed systems. They include many observations on the behaviors of SWEs.

**** DK's pagination solution
Assume: we will always display the first page of a query.
Assume: the dataset has the row index as a field.

When the first page of a query loads, record the locus-alleles and row index for the first and last
variant. Next page is easy and fast: make a request for variants after the last variant.

Nth page is slightly harder: take the index of the last variant and add =PAGE_SIZE * N=. Send that
to Hail. Hail uses the index to determine in which partition a variant exists with index
=LAST_VARIANT_INDEX + PAGE_SIZE * N=. I assume our indices let us skip a count of variants within a
partition. If not, it should not be hard to add this to our B-Tree implementation.
